# PROJECT_OVERVIEW.md — Обзор текущего состояния проекта

## Введение

Этот документ содержит детальное описание текущей архитектуры, возможностей агентов и технического состояния системы **Polymarket AI Agent Team**. Проект успешно прошел фазу создания MVP, объединения мультиагентных ролей и интеграции расширенного анализа ликвидности и корреляций.

## 1. Архитектура системы и 2-Stage Pipeline

Система работает по двухстадийному конвейеру анализа рынков, координируемому планировщиком и оркестратором **NEXUS**:

```
[Планировщик APScheduler / Команда /scan]
                   │
                   ▼
┌──────────────────────────────────────────────┐
│  Стадия 0: Скрининг и корреляции (NEXUS)     │
│  - Загрузка ~1000 compact-рынков             │
│  - Отбор Top-30 кандидатов                   │
│  - Поиск 4 видов межрыночных корреляций      │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│  Стадия 1: Загрузка полных данных            │
│  - Выгрузка деталей для Top-N рынков         │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│  Стадия 2: Мультиагентная экспертиза         │
│  - SCOUT: Оценка edge "вслепую"              │
│  - SHADOW: Анализ стакана (CLOB) + тренда    │
                       │
                       ▼
┌──────────────────────────────────────────────┐
│  Консенсус и Telegram-оповещения             │
│  - Запись сигналов при согласии экспертов    │
│  - Оповещения в реальном времени             │
└──────────────────────────────────────────────┘
```

### Стадия 0: Скрининг и поиск корреляций
*   **Оркестратор NEXUS** раз в 30 минут загружает компактный список активных рынков (до 1000 штук), используя метод `list_all_markets_compact()` адаптера, что сводит затраты на токены к минимуму.
*   NEXUS отбирает **Top-30** наиболее перспективных кандидатов и выявляет связи между ними. Поддерживаются типы корреляций:
    *   `causal` (причинно-следственная зависимость).
    *   `inverse` (противоположные рынки).
    *   `arbitrage` (ценовые расхождения).
    *   `thematic` (общая глобальная тема).
*   Результаты скрининга кэшируются в БД. О новых корреляциях бот сразу сигнализирует в Telegram.

### Стадия 1: Детальный отбор рынков
*   Система загружает полные карточки отобранных кандидатов в рамках лимита (`scan_limit`).

### Стадия 2: Мультиагентный консенсус (SCOUT ➔ SWING ➔ SHADOW)
*   **SCOUT (Математика)**: Оценивает реальную вероятность исхода вслепую (Double-Blind), рассчитывая разницу $Edge = ModelProbability - MarketPrice$. Если Edge $\ge 10\%$, идея передается дальше.
*   **SHADOW (Ликвидность)**:
    *   Запрашивает глубину стакана и спред через Polymarket CLOB API по `clobTokenId`.
    *   Анализирует **асимметрию Bid/Ask** (преобладание покупателей над продавцами) и тренд цены за последние 24 часа.
    *   Блокирует неликвидные рынки с широким спредом, где невозможен комфортный выход из позиции.
*   **Итог**: Сигнал генерируется только при взаимном согласии экспертов (уверенность SHADOW $> 0.6$).

### Стадия 3: Авторезолюция (Outcome Tracker)
*   **Опрос исходов**: Планировщик раз в 6 часов запускает цикл авторезолюции для сигналов в статусе `PENDING`, чьи рынки уже завершились (`close_time < now`).
*   **Источники данных**: Исход запрашивается напрямую через Polymarket API (с фолбеком на локальную БД).
*   **Обновление статусов**: Сигналы архивируются (`status = 'ARCHIVED'`), фиксируется `resolved_at`, `resolution_outcome` и прибыльность `was_profitable`. Исход также обновляется в таблице `markets`.
*   **Пересчет метрик**: Для всех затронутых стратегий пересчитывается Win Rate и Brier Score по скользящему окну за последние 30 дней (`strategy_metrics`).
*   **Telegram-отчеты**: В канал отправляется подробная сводка о разрешенных сигналах и обновленной точности стратегий.

## 2. Структура базы данных (SQLite)

База данных расположена по пути `vault/database.sqlite` (WAL-режим для конкурентного доступа) и включает таблицы:

1.  `markets`: данные по рынкам, дополненные полями `tokens` (список CLOB-токенов) и `volume` (объем торгов).
2.  `signals`: сохраненные итоговые сигналы (статусы: `PENDING`, `ARCHIVED`, `EXECUTED`).
3.  `agent_opinions`: вердикты и развернутые мнения экспертов (SHADOW) по рынкам.
4.  `analyzed_markets`: отметки времени и цены последнего сканирования каждого рынка для кулдауна.
5.  `price_history`: точки изменения цены для построения трендов и анализа SHADOW.
6.  `correlations`: записи об обнаруженных межрыночных зависимостях.
7.  `memory`: KV-память оркестратора (Layer 1) с поддержкой приоритетов и TTL.
8.  `chat_history`: контекст Telegram-диалогов с лимитом хранения.
9.  `vault_index`: индексация базы знаний Obsidian.

## 3. Языковые модели и оптимизация затрат

Все специализированные агенты переведены на эффективное семейство моделей Flash для снижения операционных расходов на токены:
*   **SCOUT / SHADOW / SWING**: по умолчанию используют `gemini-2.5-flash`.
*   **NEXUS**: использует `gemini-2.5-flash` по умолчанию (включая работу с инструментами Function Calling), с возможностью переключения на `gemini-3.5-flash` или тяжелую `gemini-2.5-pro` для сложных аналитических запросов через Telegram-команду `/model`.

## 4. Пользовательский интерфейс Telegram

Telegram-бот (`telegram/bot.py`) полностью интегрирован с ядром системы и поддерживает команды:
*   `/start` — запуск и приветствие.
*   `/help` — подробный справочник.
*   `/status` — мониторинг состояния агентов, планировщика и метрик БД.
*   `/scan` — интерактивный запуск сканирования по 6 категориям (включая авто-микс).
*   `/ideas` — вывод последних 5 активных сигналов.
*   `/correlations` — вывод обнаруженных межрыночных связей.
*   `/model` — быстрое переключение моделей оркестратора (рекомендуемые Flash-модели вынесены вперед).
*   `/settings` — настройка лимитов сканирования и порогов Edge.
*   `/stats` — показатели наполненности БД.
*   `/cleanup` — архивация устаревших сигналов.
*   `/logs` — вывод последних логов системы.

## 5. Развертывание и Особенности Инфраструктуры (Контекст для AI)

*   **Production Environment**: Бот крутится на удаленном **Debian сервере** как фоновый процесс (управляется менеджером вроде `systemd` или `pm2`). 
*   **Dev Environment**: Разработка и работа AI-помощника ведутся с локальной машины Windows, куда папка сервера подмонтирована как сетевой диск Z. 
*   **Процесс обновления**: Поскольку AI-агент меняет локальные файлы (примонтированные), изменения необходимо отправлять в GitHub (`git push`), после чего на Debian-сервере нужно сделать `git pull` и перезапустить процесс.
*   **Перезапуск**: Команда `/restart` вызывает `os._exit(0)`. Это штатно завершает процесс, и менеджер (systemd) мгновенно поднимает его заново.
*   **Cerebras & Rate Limits**: У бесплатных ключей Cerebras жесткий лимит 429 Too Many Requests (Tokens per minute). Из-за этого распараллеливание запросов `scout` и `swing` отключено — они работают строго по очереди. Если сервер API отвечает 429, клиент делает задержку (sleep) 20 секунд и повторяет попытку, чтобы не прерывать сканирование.
*   **Ограничение языка (Промпты)**: Опенсорсные модели (Llama 3, Nemotron, Grok) часто срываются на английский. Для каждого агента (SCOUT, SWING) прописано строгое `КРИТИЧЕСКОЕ ПРАВИЛО 2` выдавать текстовые поля в JSON строго на русском языке под угрозой штрафа.
